# Aturan Proyek SIGAP

Dokumen ini mengikat semua kontributor: anggota tim maupun asisten AI (Claude Code, Copilot, Cursor, dan sejenisnya) yang dipakai anggota tim. Asisten AI adalah alat bantu; hasil kerjanya adalah milik dan tanggung jawab anggota tim yang memakainya.

## 1. Sumber Kebenaran

1. `docs/PRD.md` adalah acuan kebutuhan untuk pengembang. SRS v1.0 (dokumen praktikum) adalah dokumen resmi di atasnya.
2. Perubahan kebutuhan diubah dulu di PRD lewat PR terpisah, baru kode menyusul. Kode tidak boleh "mendahului" PRD.
3. Teks UI, label tombol, nama field, dan pesan sistem harus persis seperti PRD Lampiran A dan B. Jangan parafrase, jangan ubah tanda baca.
4. Setiap perubahan kode harus bisa ditelusuri ke kode kebutuhan (REQ-x.y, NFR-x, BR-x). Sebutkan di deskripsi PR dan di nama test.

## 2. Git: Identitas dan Atribusi (WAJIB)

Aturan ini tidak punya pengecualian.

1. Setiap commit dibuat atas nama anggota tim yang mengerjakannya, memakai `user.name` dan `user.email` pribadi yang sudah dikonfigurasi di mesin masing-masing.
2. Dilarang menulis atribusi AI dalam bentuk apa pun di pesan commit, deskripsi PR, komentar kode, README, changelog, atau file proyek lainnya. Termasuk dan tidak terbatas pada:
   - trailer `Co-Authored-By:` yang merujuk Claude, Anthropic, Copilot, atau AI lain;
   - trailer `Claude-Session:` atau tautan sesi AI;
   - kalimat "Generated with Claude Code", "Generated by AI", emoji robot, dan sejenisnya.
3. Dilarang commit file konfigurasi asisten AI: `.claude/`, `CLAUDE.md`, `CLAUDE.local.md`, `.cursor/`, `.cursorrules`, `.github/copilot-instructions.md`, `.aider*`. Semua sudah ada di `.gitignore`. Jika terlanjur ter-track:
   ```bash
   git rm -r --cached .claude CLAUDE.md
   git commit -m "chore: remove AI assistant config from index"
   ```
4. Jangan mengubah git config proyek atau global, kecuali menjalankan `scripts/setup-hooks.sh` (bagian 2.1).
5. Pengguna Claude Code wajib mematikan atribusi bawaan di `~/.claude/settings.json` di mesin masing-masing:
   ```json
   {
     "attribution": { "commit": "", "pr": "", "sessionUrl": false }
   }
   ```
   Setting lama `"includeCoAuthoredBy": false` boleh ditambahkan untuk versi Claude Code yang lebih tua.

### 2.1 Penegakan otomatis dengan git hooks

Setelah clone, jalankan sekali:

```bash
bash scripts/setup-hooks.sh
```

Perintah itu mengarahkan `core.hooksPath` ke folder `.githooks/` yang ikut ter-commit, sehingga semua anggota tim memakai hook yang sama.

| Hook | Yang dilakukan |
|---|---|
| `commit-msg` | Menghapus otomatis baris trailer atribusi AI dari pesan commit dan memberi tahu di terminal. Menolak commit jika masih ada jejak AI di pesan, atau jika author/committer beremail `anthropic.com`. |
| `pre-push` | Memindai semua commit yang akan di-push. Menolak push jika ada commit beratribusi AI, ada file konfigurasi AI di tree, atau ada berkas `.env` (selain `.env.example`). |

Hook bisa dilewati dengan `--no-verify`, tetapi melakukannya melanggar aturan ini. Reviewer wajib menolak PR yang membawa jejak AI.

### 2.2 Memperbaiki commit yang terlanjur beratribusi

- Commit terakhir, belum di-push:
  ```bash
  git commit --amend
  ```
  lalu hapus baris yang bermasalah di editor.
- Beberapa commit, belum di-push:
  ```bash
  git rebase -i <base>
  ```
  tandai `reword` pada commit yang bermasalah.
- Sudah di-push ke branch fitur: perbaiki dengan cara di atas lalu `git push --force-with-lease`. Beri tahu anggota tim yang menarik branch itu.
- Jangan pernah force-push ke `main`.

## 3. Alur Kerja Git

### 3.1 Branch

- `main` selalu dalam keadaan bisa dijalankan. Dilindungi: tidak ada push langsung, merge hanya lewat PR.
- Satu branch untuk satu fitur, satu UC, atau satu perbaikan.
- Pola nama: `<tipe>/<kode-uc>-<deskripsi-singkat>` dalam huruf kecil dan tanda hubung.

| Tipe | Contoh |
|---|---|
| `feat` | `feat/uc-03-login-dashboard` |
| `fix` | `fix/uc-02-ticket-not-issued-on-partial-data` |
| `chore` | `chore/setup-ci` |
| `docs` | `docs/prd-update-ticket-format` |
| `test` | `test/uc-06-behat-scenarios` |

### 3.2 Pesan commit

Memakai Conventional Commits, bahasa Inggris, kalimat imperatif, subjek maksimal 72 karakter. Scope memakai kode UC jika relevan.

```
feat(uc-03): lock account after three failed login attempts

Implements REQ-3.5 and NFR-11. Lockout state is stored on the Petugas
record and cleared by an administrator.
```

Tipe yang dipakai: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `style`. Tidak ada emoji. Tidak ada trailer selain `Refs:` ke nomor isu bila ada.

### 3.3 Pull request

- Judul mengikuti format pesan commit.
- Deskripsi memuat: apa yang berubah, mengapa, kode REQ/NFR/BR yang dipenuhi, cara menguji, tangkapan layar untuk perubahan UI.
- Minimal satu reviewer dari anggota tim lain. Penulis tidak me-review PR-nya sendiri.
- CI harus hijau sebelum merge.
- Merge memakai squash agar riwayat `main` bersih. Pesan squash mengikuti aturan 3.2.
- PR kecil lebih baik. Jika satu UC terlalu besar, pecah per lapisan (entity dan migrasi, control, boundary) atau per jalur (basic path dulu, alternative path menyusul).

### 3.4 Audit sebelum push

Jalankan dan periksa sendiri sebelum `git push`:

```bash
git status
git diff --cached
git log --format='%an <%ae>%n%B' origin/<branch>..HEAD
```

Pastikan tidak ada: berkas `.env`, kredensial, API key, file AI, atau atribusi AI. Hook `pre-push` adalah jaring pengaman, bukan pengganti pemeriksaan ini.

## 4. Arsitektur dan Konvensi Kode

### 4.1 Pola Boundary, Control, Entity (NFR-18)

Kode dipisah menurut tiga lapisan dan tidak boleh saling melompat.

| Lapisan | Isi | Boleh bergantung pada |
|---|---|---|
| Boundary | Halaman, komponen UI, endpoint HTTP, handler WebSocket | Control |
| Control | Logika use case, validasi aturan bisnis, orkestrasi ke layanan eksternal | Entity, adapter eksternal |
| Entity | Model domain, enumerasi status, aturan invarian data | Tidak ada |

Nama kelas control mengikuti class diagram SRS agar mudah ditelusuri: `InformasiProdukController`, `PengaduanController`, `AutentikasiController`, `PemantauanLayananController`, `TranskripController`, `PenangananController`, `BasisPengetahuanController`, `LaporanController`. Jika framework yang dipilih memakai kata "Controller" untuk lapisan boundary, beri akhiran berbeda pada boundary (misal `...Handler` atau `...Page`) dan pertahankan nama SRS di lapisan control.

### 4.2 Penamaan

- Nama domain (entitas, atribut, status, pesan) memakai bahasa Indonesia sesuai SRS: `Pengaduan`, `Tiket`, `statusPengaduan`, `BelumDitelaah`.
- Nama teknis dan infrastruktur memakai bahasa Inggris: `repository`, `service`, `handler`, `config`, `middleware`.
- Enumerasi status wajib berupa tipe tertutup (enum atau konstanta), bukan string bebas.
- Tidak ada angka ajaib. Batas seperti "tiga kali gagal", "dua kali ulang", "30 menit" menjadi konstanta bernama yang merujuk kode kebutuhannya di komentar.

### 4.3 Adapter layanan eksternal

Semua layanan eksternal (cekbpom, LLM, STT, TTS, SMS Gateway, vector store) diakses lewat interface tunggal di lapisan control dengan minimal dua implementasi: produksi dan mock. Mock dipakai untuk pengembangan lokal, test, dan demo. Penggantian penyedia tidak boleh menyentuh kode use case.

### 4.4 API

- Respons memakai format standar `{ "status", "message", "data" }` dengan `status` bernilai `success` atau `error`.
- Kode HTTP sesuai semantik: 200, 201, 400, 401, 403, 404, 422, 500.
- Pesan error untuk pengguna dalam bahasa Indonesia sesuai kamus PRD. Detail teknis hanya di log server.
- Endpoint dashboard wajib di balik middleware autentikasi. Endpoint ekspor wajib memeriksa hak ekspor.

### 4.5 Konfigurasi dan rahasia

- Semua konfigurasi lewat environment variable. Tidak ada kredensial, API key, atau URL privat di kode.
- `.env.example` wajib ada dan selalu diperbarui saat ada variabel baru, dengan nilai placeholder.
- `.env` dan turunannya tidak pernah di-commit.

### 4.6 Kebersihan kode

- Tidak ada `console.log`, `print`, `dd()`, atau kode debug di kode yang di-merge.
- Tidak ada kode yang dikomentari "untuk nanti". Hapus, atau buat isu.
- Tidak ada fitur di luar PRD. Ide baru masuk ke isu, bukan ke PR.
- Linter dan formatter (ditetapkan setelah stack dipilih, bagian 8) harus bersih sebelum PR dibuka.

## 5. Keamanan

Mengoperasionalkan NFR-10 sampai NFR-15, OR-2, dan OWASP Top 10.

1. Password di-hash dengan algoritma modern (argon2id atau bcrypt). Tidak ada penyimpanan plaintext, tidak ada log password.
2. Kunci akun setelah tiga kali gagal berturut-turut. Hitung per akun, reset setelah login sukses. Login juga diberi rate limit per IP.
3. Sesi berakhir setelah 30 menit idle. Cookie sesi `HttpOnly`, `Secure`, `SameSite=Lax` atau lebih ketat.
4. Otorisasi di server: setiap endpoint dashboard memeriksa sesi, endpoint ekspor memeriksa hak ekspor. Jangan pernah mengandalkan penyembunyian tombol di UI.
5. Masking data pribadi (nama, nomor telepon, NIK) dilakukan di server sebelum data dikirim ke dashboard. Frontend tidak pernah menerima nilai mentah.
6. Validasi semua input di server: tipe, panjang, format, nilai enumerasi. Pakai parameterized query atau ORM. Escape semua output HTML.
7. Perlindungan CSRF pada semua form dan request pengubah data.
8. TLS 1.2 atau lebih baru di semua jalur, termasuk WSS dan panggilan ke layanan eksternal.
9. Jawaban legalitas produk hanya berasal dari hasil tool calling. Prompt sistem LLM wajib melarang penyebutan nomor izin edar tanpa hasil tool dan melarang nasihat medis. Keduanya diuji otomatis.
10. Log tidak boleh berisi data pribadi mentah, transkrip utuh, token, atau rahasia. Log memakai identifier internal.
11. Dependensi dipindai kerentanan di CI. Versi dikunci lewat lockfile.
12. Pesan error ke pengguna tidak membocorkan stack trace, nama tabel, atau detail infrastruktur.

## 6. Pengujian dan Definition of Done

### 6.1 Lapisan uji

| Lapisan | Cakupan minimum |
|---|---|
| Unit | Setiap kelas control dan aturan bisnis BR-1 sampai BR-8, termasuk jalur gagal. |
| Integrasi | Endpoint API dengan basis data uji dan adapter eksternal versi mock. |
| Penerimaan | Semua skenario Gherkin dari SRS Appendix F per UC, dijalankan otomatis (Behat atau kerangka padanan yang disepakati lewat ADR). |
| Keamanan | Uji login lockout, kedaluwarsa sesi, akses tanpa sesi, akses ekspor tanpa hak, masking PII. |

Nama test menyebut kode kebutuhan, contoh `test_req_3_5_locks_account_after_three_failures`.

### 6.2 Definition of Done

Sebuah fitur selesai jika semua poin berikut terpenuhi:

- Semua REQ pada UC terkait terpenuhi dan skenario Gherkin lulus.
- Unit dan integration test lulus; tidak ada test yang di-skip tanpa alasan tertulis.
- Pesan UI dan label sesuai kamus PRD, diperiksa manual.
- Tidak ada error atau warning di konsol browser dan log server saat jalur utama dijalankan.
- Linter dan formatter bersih.
- Dokumentasi diperbarui jika perilaku berubah: PRD, README, `.env.example`.
- PR disetujui minimal satu reviewer dan CI hijau.
- Tidak ada jejak AI dan tidak ada rahasia di diff.

## 7. Dokumentasi

- `README.md`: tujuan proyek, prasyarat, cara setup, variabel env, cara menjalankan, cara menguji.
- `docs/PRD.md`: kebutuhan produk, selalu mutakhir.
- `docs/decisions/NNNN-judul.md`: catatan keputusan arsitektur (ADR) singkat untuk setiap keputusan yang sulit dibatalkan: pilihan stack, penyedia LLM/STT/TTS, skema ID dan tiket, kerangka uji penerimaan. Format: konteks, keputusan, alternatif, konsekuensi.
- Setiap butir di PRD Bagian 15 (belum ditetapkan) diselesaikan lewat ADR, lalu PRD diperbarui.
